## 二、P1：区分读取失败、文件不存在与空库

### 2.1 问题是什么

目前审查到的逻辑中，`lib/store-core.mjs` 的 `读一份(path)` 在遇到 `EACCES`、`EBUSY`、`EIO` 等非 `ENOENT` 错误时，会记录诊断日志并返回 `blank()`。

随后类似下面的判断：

```
const 读好 = (v) =>
  v && v.ok !== false && Array.isArray(v.memories);
```

会把带有 `memories: []` 的空结构当成成功读取。

这会混淆两个完全不同的事实：

- 文件确实不存在：可以按首次初始化处理。
- 文件存在，但读取失败：当前并不知道里面有什么，绝不能当成空库。

如果把读取失败当成空库，后续镜像同步或写入流程就可能把“未知的数据状态”误认为“确定的空数据状态”，造成覆盖或清空风险。

### 2.2 建议的数据返回语义

建议让读取函数返回明确的结果对象，而不是用空库结构兼任错误兜底。

```
// 成功读取
{
  ok: true,
  missing: false,
  data: store
}

// 文件不存在：可识别的初始化状态
{
  ok: true,
  missing: true,
  data: blank()
}

// 真实读取错误：数据状态未知
{
  ok: false,
  error: {
    code: "EACCES",
    message: "Permission denied"
  }
}
```

关键原则：

1. `ENOENT` 可以表示文件尚未创建，但不能把其他错误都归类为不存在。
2. `EACCES`、`EIO`、`EBUSY`、JSON 解析失败等情况，应保留为失败状态。
3. 失败状态不能进入自动镜像覆盖、空库初始化或正常写入流程。
4. 只有显式、可审计的恢复操作，才允许用户决定用某份数据覆盖另一份数据。

### 2.3 实现参考

```
import { readFile } from "node:fs/promises";

export async function readStore(path) {
  let raw;

  try {
    raw = await readFile(path, "utf8");
  } catch (error) {
    if (error?.code === "ENOENT") {
      return {
        ok: true,
        missing: true,
        data: blank(),
      };
    }

    return {
      ok: false,
      error: {
        code: error?.code ?? "UNKNOWN",
        message: String(error?.message ?? error),
      },
    };
  }

  try {
    const data = JSON.parse(raw);

    if (!isValidStore(data)) {
      return {
        ok: false,
        error: {
          code: "INVALID_STORE",
          message: "Store schema validation failed",
        },
      };
    }

    return {
      ok: true,
      missing: false,
      data,
    };
  } catch (error) {
    return {
      ok: false,
      error: {
        code: "INVALID_JSON",
        message: String(error?.message ?? error),
      },
    };
  }
}
```

调用方也必须显式处理三种状态：

```
const result = await readStore(storePath);

if (!result.ok) {
  // 记录错误并停止依赖该数据的写入/同步操作。
  // 不允许把它降级成 blank() 后继续。
  throw new StoreReadError(result.error);
}

const store = result.data;

if (result.missing) {
  // 可以走首次初始化逻辑，
  // 但仍应遵循原有初始化与备份策略。
}
```

不要再用 `Array.isArray(v.memories)` 作为读取成功的唯一判据。结构有效性和 I/O 是否成功是两件事，应分别表达。

### 2.4 必须补的测试

| 场景         | 模拟方式                      | 预期结果                       |
| ---------- | ------------------------- | -------------------------- |
| 文件不存在      | `readFile` 抛出 `ENOENT`    | `ok: true, missing: true`  |
| 权限拒绝       | 抛出 `EACCES`               | `ok: false`，不得初始化空库        |
| I/O 故障     | 抛出 `EIO`                  | `ok: false`，不得写镜像          |
| 文件占用       | 抛出 `EBUSY`                | `ok: false`，不得覆盖原文件        |
| JSON 损坏    | 内容不是合法 JSON               | `ok: false`，保留原文件供诊断       |
| schema 不合法 | JSON 可解析但结构错误             | `ok: false`                |
| 正常空库       | 合法 store 且 `memories: []` | `ok: true, missing: false` |

建议增加一个端到端故障注入测试：主库读取失败时，确认镜像同步、自动修复、备份回写和任何“以空库为输入”的写入路径都不会执行。

## 三、P1：五个批量 LLM 路由采用字段级并发保护

### 3.1 为什么重新读取最新库仍不够

目前的改进方向是正确的：LLM 请求等待期间，不再拿旧快照整库覆盖；模型返回后重新读取最新库，并按 ID 更新。

但“按 ID 更新”只能避免整条记录被覆盖，不能自动避免同一条记录中某个字段被覆盖。

例如：

1. 请求开始时，记忆的 `category` 是 `misc`。
2. 插件把内容发给 LLM，请求尚未返回。
3. 用户手动把 `category` 改为 `identity`。
4. LLM 返回旧判断，认为它应该是 `preference`。
5. 如果无条件写入，用户刚才的修改就丢失了。

正确做法是：按字段比较请求前的旧值与返回时的当前值，只更新期间没有被其他操作修改过的字段。

### 3.2 通用字段级 patch 方案

在发起 LLM 请求前，记录目标记录和目标字段的快照：

```
const before = new Map(
  targets.map((item) => [
    item.id,
    {
      category: item.category,
      importance: item.importance,
      related: structuredClone(item.related ?? []),
      type: item.type,
      content: item.content,
    },
  ])
);
```

LLM 返回后重新读取最新库，对每个字段单独做 compare-and-set：

```
function sameValue(a, b) {
  return JSON.stringify(a) === JSON.stringify(b);
}

function applyFieldIfUnchanged({
  current,
  before,
  patch,
  field,
}) {
  if (!(field in patch)) return false;

  // 等待期间字段已经被其他操作修改：跳过。
  if (!sameValue(current[field], before[field])) {
    return false;
  }

  current[field] = patch[field];
  return true;
}
```

应用时不要直接把模型返回对象整体 `Object.assign` 到当前记忆：

```
const latest = await loadLatestStore();

for (const patch of llmPatches) {
  const current = latest.memories.find((m) => m.id === patch.id);
  const snapshot = before.get(patch.id);

  if (!current || !snapshot) continue;

  applyFieldIfUnchanged({
    current,
    before: snapshot,
    patch,
    field: "category",
  });

  applyFieldIfUnchanged({
    current,
    before: snapshot,
    patch,
    field: "importance",
  });
}

await saveStore(latest);
```

上面是概念性参考。实际实现应使用项目现有的深比较、写锁、版本号和保存接口，不要为了示例代码另造一套并行存储机制。

### 3.3 五个路由的字段冲突规则

| 路由                | LLM 可能修改的字段               | 等待期间发生冲突时                 |
| ----------------- | ------------------------- | ------------------------- |
| `/refine`         | 正文、提炼结果及其派生字段             | 用户改过正文或目标字段，就跳过对应字段       |
| `/wash-keys`      | key、关键词、规范化字段             | 只更新未被改动的关键词字段             |
| `/expand`         | `related` 等关联字段           | 用户改过 `related`，跳过模型旧结果    |
| `/classify-types` | `type`                    | 用户已经设置或修改 `type`，模型结果不得覆盖 |
| 长期设定补充            | `category`、`importance` 等 | 用户改过哪个字段，就只跳过哪个字段         |

特别注意：

- `undefined`、字段缺失、`null` 和空数组可能有不同语义，比较时要保留差异。
- 数组字段不能只比较引用，应按项目约定做稳定深比较。
- 如果用户删除了目标记忆，LLM 返回后必须发现该 ID 已不存在，并跳过更新。
- 如果目标记忆被撤销、合并或替换，不能只凭旧 ID 猜测它仍然有效。
- 冲突跳过应有可观测结果，例如返回 `appliedFields`、`skippedFields`，方便 UI 告诉用户哪些结果没有应用。

### 3.4 建议的统一返回结构

```
{
  ok: true,
  applied: [
    {
      id: "memory-id",
      fields: ["importance"]
    }
  ],
  skipped: [
    {
      id: "memory-id",
      fields: ["category"],
      reason: "changed_during_llm"
    }
  ],
  missing: [
    {
      id: "deleted-memory-id",
      reason: "record_not_found"
    }
  ]
}
```

### 3.5 并发交错测试

每个路由至少覆盖以下交错：

1. LLM 请求发出。
2. 测试暂停 LLM 响应。
3. 用户或另一个操作修改目标字段。
4. 释放 LLM 响应。
5. 检查最新库。

验收标准：

- 被修改的字段保留并发操作的值。
- 没有冲突的字段可以正常应用。
- 已删除的记录不会被模型结果复活。
- 一次批量任务不能把旧快照整库写回。
- 失败或部分跳过的结果可以被记录和解释。

## 四、P1：检查 `restoreIds` 与并发删除冲突

### 4.1 风险描述

现有合并逻辑中，显式 `restoreIds` 找回操作可能在并发场景下撤销另一处刚发生的删除。

例如：

1. 撤销操作读取到记录 A 曾经存在。
2. 另一处操作删除了记录 A。
3. 撤销操作稍后提交 `restoreIds: [A]`。
4. 如果恢复逻辑没有检查删除发生的代际或版本，就可能把 A 重新放回去。

这不是普通的撤销历史记录问题，而是两个并发操作对同一条记录的意图冲突。

### 4.2 可选防护方式

优先考虑项目已有的版本号、代际或删除标记，不建议为了局部修复引入复杂的新机制。

可选方案：

- 版本比较：撤销时记录目标记录版本；提交时只有版本仍匹配才恢复。
- 删除代际：记录删除发生时的 generation；旧撤销请求不能跨越更新的删除代际。
- 墓碑记录（tombstone）：删除先写入带版本的墓碑，恢复操作必须明确针对该墓碑版本。

伪代码示意：

```
function canRestore(snapshot, latest) {
  if (!latest) return false;

  return (
    latest.deleted === true &&
    latest.deleteVersion === snapshot.expectedDeleteVersion
  );
}
```

具体字段应按现有数据结构确定。核心要求是：恢复操作必须证明自己要恢复的，仍然是它当初观察到的那次删除，而不是后来另一处操作新产生的删除。

### 4.3 测试矩阵

| 并发场景           | 预期                    |
| -------------- | --------------------- |
| 撤销期间没有新操作      | 正常恢复                  |
| 撤销期间同一记录再次被删除  | 旧撤销不得恢复新删除            |
| 撤销期间记录被编辑      | 按项目定义的冲突策略处理          |
| 撤销期间记录已被永久清理   | 不得凭旧快照无条件复活           |
| 两个撤销操作同时恢复同一记录 | 最多一个成功提交，另一个识别冲突或幂等结束 |

## 五、P2：工作区级记忆 scope

当前已知 scope 主要是 `global` 和 `session`。这不足以表达“个人记忆跨工作区共享，但项目知识在同一工作区的不同会话间共享”。

建议未来明确区分三层：

| Scope            | 可见范围      | 典型内容                  |
| ---------------- | --------- | --------------------- |
| `global`         | 所有工作区     | 用户长期偏好、稳定身份信息、跨项目长期约定 |
| `workspace:<id>` | 同一工作区内的会话 | 当前项目架构、项目决策、项目术语、待办事项 |
| `session:<id>`   | 当前会话      | 临时上下文、尚未确认的草稿、短期讨论状态  |

不要简单把 `session` 改成 `workspace`。两者生命周期不同，session 级临时信息不应自动升级为项目长期知识。

### 5.1 访问规则建议

- 默认允许工作区读取 `global`。
- 工作区只能读取自己的 `workspace:<id>`。
- 默认不允许工作区 A 读取工作区 B 的项目记忆。
- 当前会话可读取自己的 session 记忆。
- 写入时根据内容归属选择 scope；不确定时先保持在较窄范围，避免过度共享。
- scope 变更应是显式迁移，不应因为一次召回或总结就自动跨层复制。

### 5.2 记忆归属判断示例

- “我更喜欢先看风险再做优化”——可能是 `global` preference，但应有足够证据。
- “Clay Memory 的主库使用独立 JSON 存储”——属于该项目的 `workspace:<clay-memory-id>`。
- “刚才这次请求先不要执行写入”——通常属于 `session`。
- “我正在开发一个项目”——仅凭这句话不代表项目细节应进入 global。

# 六、P2：`inference` 推测型记忆——定义与用途

这是本阶段需要向模型解释清楚的概念。建议把本节作为实现和提示词设计的共同依据。

## 6.1 一句话定义

`inference` 不是用户明确说过的事实，而是系统根据若干条已有证据，暂时推导出的、可能有助于未来协作的判断。

更口语一点：

> 它不是“AI 认为用户是什么样的人”，而是“AI 根据目前有限的证据，暂时形成的一个可能有用、但允许被推翻的判断”。

它必须被标记为推测，不能伪装成用户原话，也不能与用户明确表达的事实混在一起。

## 6.2 为什么需要单独类型

普通记忆通常记录：

- 用户明确说过什么；
- 用户明确选择了什么；
- 项目中已经确定了什么；
- 某件经历实际发生过什么。

但长期协作中还有一类信息：用户没有直接说出来，系统却可能从多次行为中观察到某种规律。

例如：

- 用户连续几次在改动前先要求检查数据安全风险。
- 用户在多个项目中都倾向于先做最小可行版本，再逐步扩展。
- 用户遇到不确定的工程问题时，常常先要求定位根因，而不是直接重写。

这些规律可能对未来协作有帮助，但它们仍然只是基于有限样本的归纳。系统不能把它们写成“用户明确要求”或“用户永远如此”。

因此需要一个单独的 `inference` 类型，明确表达其证据来源、置信程度和有效边界。

## 6.3 与其他记忆类型的区别

| 类型             | 记录什么               | 示例                               |
| -------------- | ------------------ | -------------------------------- |
| `identity`     | 用户明确表达的稳定身份或背景信息   | “我是一名后端开发者”                      |
| `preference`   | 用户明确表达的偏好          | “我更喜欢先看简短结论，再看细节”                |
| `experience`   | 实际发生过的经历           | “我们上周一起排查了基线数据为空的问题”             |
| `agreement`    | 双方明确约定的规则          | “修改真实环境前必须先征求确认”                 |
| `relationship` | 用户明确表达或双方明确建立的关系语境 | “这个项目是我们持续维护的长期项目”               |
| `inference`    | 根据证据推导出的暂时判断       | “从近期几次代码审查看，用户在数据迁移任务中可能更重视可回滚性” |

判断规则：

- 用户直接说“我喜欢 X”——优先记为 `preference`，不是 inference。
- 用户说“我总是先做 A 再做 B”——如果作为用户自述记录，可记为明确表达的习惯；不要无必要地再推测一次。
- 系统从多次行为观察到“用户似乎倾向于 A”——才考虑 `inference`。
- 单次行为通常不足以形成长期推测。
- 推测不应被包装成诊断、人格定论或心理标签。

## 6.4 具体场景：什么情况下值得写入

### 场景 A：工作流程倾向

观察到用户在多个独立任务中，反复要求先确认风险和回滚方案，再执行批量修改。

可以暂时记录：

> 推测：用户在涉及批量数据变更的工程任务中，可能偏好先明确风险和回滚路径，再执行修改。

不能扩大成：

> 用户是一个极度保守、害怕变化的人。

前者限定在具体任务场景，并且可以被新证据推翻；后者是宽泛人格判断，证据不足。

### 场景 B：技术协作方式

观察到用户多次要求先给出问题定位、复现条件和验收标准，再讨论代码改动。

可以暂时记录：

> 推测：在技术排障任务中，用户可能更喜欢“根因分析—最小修复—回归验证”的讨论顺序。

不能写成：

> 用户讨厌直接给代码。

用户可能在简单问题上恰恰希望直接得到代码。

### 场景 C：项目决策倾向

观察到用户在某个项目里多次选择保留旧数据、渐进迁移和显式确认。

可以记录为：

> 推测：在该项目的数据迁移场景中，用户可能优先考虑数据可恢复性。

注意限定在“该项目”和“数据迁移场景”，不要自动推广到用户所有项目。

## 6.5 反例：哪些内容不应成为 inference

以下情况不应写入长期推测：

1. 单次行为：用户今天熬夜，不代表用户长期作息混乱。
2. 情绪瞬间：用户一次表达烦躁，不代表用户性格暴躁。
3. 缺乏证据的动机猜测：用户拒绝某个方案，不代表用户害怕改变或不信任 AI。
4. 敏感属性推断：不能从零散行为推断健康、宗教、政治立场、性取向等敏感属性。
5. 把模型偏见当用户特征：不能因为用户使用某种工具、语言或表达方式，就套用群体刻板印象。
6. 把项目要求推广为个人偏好：用户在一个项目中要求严格测试，不代表所有场景都必须严格测试。
7. 把助手自己的建议当成用户认同：助手提出某种判断，用户没有确认，不构成用户证据。

## 6.6 每条 inference 应保存什么

建议结构如下。字段名可以按项目现有命名风格调整：

```
{
  id: "inf_xxx",
  type: "inference",

  // 推测内容：必须使用“可能、倾向、在某场景下”等限定语
  statement: "在批量数据变更任务中，用户可能更重视可回滚性",

  // 支撑这条推测的证据，引用已有记忆 ID，不复制成用户原话
  evidence: [
    {
      memoryId: "mem_001",
      relation: "supports"
    },
    {
      memoryId: "mem_019",
      relation: "supports"
    }
  ],

  // 0~1 的内部估计值，不是客观概率，也不是事实正确率
  confidence: 0.72,

  // 推测适用范围，避免跨场景泛化
  scope: {
    level: "workspace",
    id: "clay-memory"
  },

  // 形成时间与最近复核时间
  createdAt: "2026-10-01T10:00:00.000Z",
  reviewedAt: "2026-10-01T10:00:00.000Z",

  // 可用于反驳或修正推测的证据
  counterEvidence: [],

  // 生命周期状态
  status: "active",

  // 明确说明这不是用户原话
  provenance: "model_inference"
}
```

字段设计说明：

- `statement`：用有限定范围的语言表达，不写绝对结论。
- `evidence`：关联已有记忆 ID，方便追溯；证据被删除或失效时要重新评估。
- `confidence`：表示系统当前对该推测的内部把握程度，不应展示成精确科学概率。
- `scope`：限定适用范围。工作区内观察到的倾向，默认只在该工作区使用。
- `createdAt` / `reviewedAt`：区分推测何时形成、何时被重新检查。
- `counterEvidence`：保存与推测相冲突的事实或记忆。
- `status`：至少支持 `active`、`needs_review`、`superseded`、`rejected`。
- `provenance`：明确区分模型推测与用户明确陈述。

如果当前 schema 不适合一次加入所有字段，可以先做最小版：`statement`、`evidence`、`confidence`、`scope`、`status`、`createdAt`。但不要省略“这是推测”的来源标记。

## 6.7 置信度怎么用

置信度不是“模型说了 0.9 就一定有九成正确”。它只是帮助系统控制推测的使用强度。

建议采用保守分层：

| 置信度   | 处理建议                                   |
| ----- | -------------------------------------- |
| 低     | 不写入长期记忆，或只保留为当前会话临时观察                  |
| 中     | 可保存为待复核推测，不主动用于个性化决策                   |
| 较高    | 可在明确相关的场景中作为弱提示，仍需保留推测措辞               |
| 与反证冲突 | 降低置信度或标记 `needs_review`，不能只因旧证据多就忽略新反证 |

不要只靠出现次数累加置信度。同一事件被多次总结、复制或重复召回，不应被当成多份独立证据。

## 6.8 写入规则

建议模型在写入 inference 前，依次检查：

1. 是否有至少两条相对独立的证据？若只有一次行为，通常不写。
2. 证据是否来自用户实际表达或行为，而不是助手自己的推断？
3. 是否存在相反证据？
4. 推测是否有明确适用场景？
5. 未来是否真的有机会帮助协作？如果没有实际用途，就不写。
6. 是否涉及敏感属性或不适当的心理、人格判断？若是，不写。
7. 是否能用谨慎、可推翻的语言表达？若不能，不写。

伪代码：

```
function shouldCreateInference(candidate) {
  if (candidate.isSensitiveAttribute) return false;
  if (candidate.evidence.length < 2) return false;
  if (!candidate.scope) return false;
  if (!candidate.hasPracticalUse) return false;
  if (candidate.isAssistantOnlyAssumption) return false;

  return true;
}
```

这里的“两条证据”是保守的初始门槛，不是数学定律。若两条证据其实来自同一事件的重复摘要，仍然只算一条。

## 6.9 召回规则：默认不注入

这是 `inference` 最重要的安全边界。

普通记忆召回时，不应把所有 inference 自动拼进系统提示词。

建议：

- 默认只召回明确事实、偏好、约定和当前项目记忆。
- 只有当当前任务与某条 inference 的 scope 和主题都相关时，才考虑召回。
- 召回时必须保留推测措辞，例如“历史行为显示，用户在这类任务中可能偏好……”。
- 不得把 inference 改写成“用户要求……”或“用户就是……”。
- 如果 inference 与用户当前明确表达冲突，以用户当前明确表达为准。
- 不允许仅凭 inference 自动执行高影响操作，例如删除、覆盖、发送、购买或修改真实环境。

示例：

不合适的注入：

> 用户非常保守，不喜欢冒险。请始终避免提出新方案。

合适的注入：

> 在此前几次批量数据变更任务中，用户曾优先要求回滚方案。该推测仅适用于类似的数据变更场景；如当前用户明确要求快速试验，应以当前指令为准。

## 6.10 更新、反证、降级和失效

推测型记忆不能只增不减。建议支持完整生命周期：

- 强化：出现新的、独立且一致的证据，可以提高置信度。
- 反证：出现相反证据，降低置信度并记录反证。
- 范围收窄：发现推测只在某个项目或任务类型中成立，应缩小 scope。
- 待复核：证据过旧、上下文变化或证据来源被删除时，标记 `needs_review`。
- 替代：更准确的新推测形成后，旧推测标记 `superseded`，保留来源关系。
- 否定：用户明确指出推测错误时，标记 `rejected`，不得继续召回。
- 删除：用户要求删除时，按普通记忆删除流程处理，并清理或重新评估依赖它的推测。

用户明确表达永远优先于系统推测。用户说“这次我就是想先快速试验”，不能被旧推测挡住。

## 6.11 推荐的最小实现版本

第一版不必做复杂的自动置信度学习。建议先实现：

1. schema 增加 `type: "inference"`。
2. 增加 `evidence`、`confidence`、`scope`、`status`、`provenance`。
3. 写入时要求至少两条独立证据，且必须标记适用范围。
4. 默认不进入普通自动召回。
5. 只有显式相关查询才允许召回，并在结果中标明“推测”。
6. 用户当前明确表达与推测冲突时，当前表达优先。
7. 提供查看、确认、纠正、拒绝和删除入口。
8. 增加反证和失效测试。

第一版甚至可以不自动生成 inference，只允许内部测试或人工确认后写入。先验证类型隔离和召回边界，再考虑自动归纳。

## 七、P2：benchmark 路径可移植性

当前脚本已经支持环境变量：

- `BENCH_SESSION_ID`
- `BENCH_PORT`
- `BENCH_QUERIES`
- `BENCH_OUTPUT`
- `BENCH_BACKEND`

但默认问句和输出路径仍绑定 `G:/tmp/bench/...`。建议将默认路径改为相对脚本或项目根目录的路径。

示意：

```
import path from "node:path";
import { fileURLToPath } from "node:url";

const here = path.dirname(fileURLToPath(import.meta.url));
const projectRoot = path.resolve(here, "../..");

const defaultQueries = path.join(
  projectRoot,
  "tools",
  "bench",
  "queries.json"
);

const defaultOutput = path.join(
  projectRoot,
  "tools",
  "bench",
  "S0-baseline.json"
);

const queriesPath = process.env.BENCH_QUERIES ?? defaultQueries;
const outputPath = process.env.BENCH_OUTPUT ?? defaultOutput;
```

实际相对层级应按脚本文件位置核实。不要直接照抄 `../..` 而不检查目录结构。

验收：

- Windows、Linux、macOS 均可使用默认路径。
- 环境变量仍能覆盖默认路径。
- 路径中包含空格或中文时可正常运行。
- 输出目录不存在时，按项目既定策略创建或报错，不要静默写到其他位置。

> 第五，单独设计 `workspace:<id>` scope，使同一工作区的会话能够共享项目记忆，同时继续隔离不同工作区的项目私有信息。不要简单把 session scope 改名为 workspace scope。

## 十一、最后强调：不要让推测冒充记忆

`inference` 的价值不是让系统更大胆地“读懂用户”，而是让系统能够诚实地保存那些有用、但尚未被用户确认的观察。

它应该让记忆系统更谨慎，而不是更武断：

- 事实有事实的来源。
- 偏好有偏好的来源。
- 经历有经历的上下文。
- 推测明确标注为推测。
- 反证可以改变结论。
- 用户可以纠正或拒绝。
- 当前表达始终高于历史推测。

如果做不到这些，宁可暂时不写入 `inference`。一个会承认“我只是这样推测”的记忆系统，比一个把猜测说成“我一直都知道你”的系统可靠得多。
