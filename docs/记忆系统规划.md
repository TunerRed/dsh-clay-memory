## 0. 一页纸

**要解决的问题**：现在的记忆只有「是不是事实」一条线------要么永不淡忘且全局共享，要么只属于一个会话。它分不清「我的身份」和「某天发生的事」，记错了删起来要五步，被想起来的时候用户完全看不见。

**最终形态**：

-   记忆按**持久度**分三层：核心（每轮必带）/ 常规（检索到就带）/
    会话私事（只在那个会话里）
-   三层都**不删**，淡的只是召回排序；被别的会话重新聊到会**回血**
-   会话结束后**自动整理**（dream）：有价值的进全局、旧的合并归纳、能整批撤销
-   已经发生过但尚未被黏土记忆整理的**历史会话可以事后补记**：重新提取候选记忆，与现有全局记忆汇合，先预览再写入，可整批撤销
-   用户能随时**看见**（想起了几条）、**问**（你记得我什么）、**忘**（忘掉这个）、**管**（一个列表 +
    作用域徽章）
-   存储换成 SQLite（`node:sqlite`），事务兜住回血、整理、撤销

**不在本次范围**：向量召回、多用户、云端同步、跨实例共享库。

## 2. 记忆模型

### 2.1 三个维度（正交）

  ------------------------------------------------------------------------
  维度                    取值                    决定什么
  ----------------------- ----------------------- ------------------------
  **领域**                身份 / 关系 / 约定 /    给人看、给检索加权
                          偏好 / 经历 / 杂项     

  **持久度**              核心 core / 常规 normal 衰减速度、是否每轮注入
                          / 易逝 volatile        

  **作用域**              全局 global / 会话      谁看得见
                          session                
  ------------------------------------------------------------------------

**领域 → 持久度的默认映射由代码做，不由模型判**：身份 / 关系 / 约定 默认
core；偏好 / 经历 / 杂项 默认
normal。模型只在「例外」时写理由，例外进人审队列。
（理由：让模型同时输出两个共线标签，只会「一致地错」，靠标签冲突检测不出来。）

### 2.2 三层半衰期

  ---------------------------------------------------------------------------------------------------------------
  层                内容                           鲜活度                                注入方式
  ----------------- ------------------------------ ------------------------------------- ------------------------
  **core**          身份、关系、约定、纠正         恒定                                  每轮固定，独立字数预算
                                                   `A = 1`，不参与衰减计算，情绪项归零  

  **normal**        一起经历过的事、有结论的讨论   慢衰减，被聊到**回血**                检索命中才带

  **volatile**      会话里的琐事                   不衰减（但只在会话内可见）            重开该会话时按鲜活度排
  ---------------------------------------------------------------------------------------------------------------

### 2.3 淡忘的语义

-   **保留**（不删、不归档）与**召回**（按鲜活度排）是两件事：久了排后面，排到就能出现。
-   衰减公式用 **lazy decay**：只存 `(activation, activation_at)`，读时
    `A = activation * 2^(-(now - activation_at) / H)`，写时先结算、再改、再写。
    **`activation_at` 是「上次结算时刻」，不是「事情发生时刻」。**
-   两个时间必须分开存：`m.at`（事情发生时间，决定「3 天前」的说法）vs
    `activation_at`（活跃度锚）。

### 2.4 回血

**触发点必须是「用上了」，不能是「召回了」。** 实测注入按模型步调用（75
分钟 1023 次，同一秒同 query 最多 12 次），挂在召回上会被乘 30 倍 →
自激（core 每轮注入 → 每轮加分 → 永不衰减）。

-   判定沿用现有 `用上了()`：reply 与记忆实词重合 ≥2 且比例 ≥1/3
-   **节流**：每条记忆每个会话每小时最多回血一次
-   回血是幂等单行 UPDATE，失败只记 diag，**不阻塞注入**

### 3.1 写入三档

  情况       处理                         例子
  ---------- ---------------------------- ------------------------
  稳定属性   保留，不因单次事件改写       用户对助手的一句正面评价
  单次事件   新增带日期，挂在稳定属性下   今天因为某事被骂大笨鱼
  明确指令   覆盖旧事实                   「以后别这样称呼我」

判定顺序（**明确指令排第一**，原方案排错了）： 1.
**明确指令**（祈使结构 + 持续性副词 + 明确指代，三条齐全才升 core） 2.
时间词 → 单次事件 3.
评价对象（谓词是一次性动作→事；恒常属性且主语是人→人） 4.
同类事件**跨会话累计 ≥3 次**才归纳倾向（**计数由代码做，模型只读
`count=N` + 证据 id**） 5. 与既有事实冲突时，走 3.2
的合并规则，不直接覆盖

### 3.2 冲突与覆盖

-   **覆盖挂到事实键**（`对象.方面`）：同键同槽不同值 → 旧值
    `invalid_at`，新值 `valid_at`，**两条都留着**（借 Zep
    的双时间轴，失效不删除）
-   不同键 → 新增
-   **禁止对「人」使用全称量词**（总是 / 从来 / 每次 /
    一直），只允许用于规则条文（正则拦）

### 3.3 模式层（反复正负评价）

  --------------------------------------------------------------------------------------
  档                      内容                    存不存
  ----------------------- ----------------------- --------------------------------------

-   交替率判读：一周内交替 \>5 次 → 「表达方式」；跨月才交替 5 次 →

-   写入格式 ≠ 注入格式：写入可含推测，注入只允许事实和观察

#### 3.5.1 假设入库前的三道闸（2026-11-18 落地为工具）

写这一段时（2026-11-18）dream 本体还没开工——1.12.55 起它上线了，1.12.68 又把「思考吃光输出预算」修掉，这个前提已经变了；下面记的是「怎么判断一条归纳是真的」这件事，它先做成了可跑的闸门：
`tools/check-hypothesis.mjs`。拿一句假设去问库里有没有证据，回答分三档
（支持 / 反例 / 存疑）。

起因是**两次当场被打脸**：

- 「主人喜欢在晚上聊松的话题，白天正经」—— 主人原话（已脱敏：大意是多数时候放松，正经多半是装的）。错的不是观察，是**归因**：变量不是时间，是「有没有工作压着」。
- 「他说『你定』是一种测试」—— 主人原话（已脱敏：大意是让我定是因为相信我的技术判断）。「测试」这个动机标签**没有任何客观行为能支撑**，是我自己脑补完再拿证据去凑。

三道闸门对应两种病史：

| 闸门 | 拦什么 | 怎么判 |
| --- | --- | --- |
| 词面支持 | 连边都不沾的假设 | 有共词（过滤停用词）才算一条支持证据 |
| 矛盾词检测 | 方向相反的旧记忆 | 喜欢↔不喜欢、晚上↔白天、正经↔松… 命中即标「反例」 |
| 跨日期聚合 | **同一天堆出来的样本** | 支持证据全挤在 1 个日期 → 判「不足以当规律」 |

**第三条最贵**。第一次归纳那三条「晚上的证据」其实落在同一两天里，等于**一个样本被拆成了三条**。工具现在会明说：一个日期里连续发生的几件事，很可能只是同一件事的不同侧面，等它在别的日期再出现一次再算数。

**工具能做什么 / 不能做什么**：能抓「记忆里明确写了相反情况」的；抓不住「记忆里根本没提过」的。所以它的结论只有「粗判」——**找到支持 ≠ 假设成立**，最终裁定权还在人（和 dream 的状态机）。

dream 一旦开写，这三道闸就是 3.5 里「推论写成事实」「过度归纳」两行的**代码实现**，不是另起一套。


### 3.6 历史会话补记（backfill）与跨会话汇合

**问题**：黏土记忆安装前、全局记忆能力上线前，或某次会话未启用记忆时，历史会话里已经发生的内容不能因为"当时没记"而永久丢失。旧记忆插件导出的记忆与历史会话原文是两类不同来源：前者是
**memory → memory** 迁移，后者是 **conversation → memory**
提炼，不能混成一次大模型总结。

**原则**：

1.  **不合并会话本身，只汇合记忆。** 原会话保持原样；补记只产生候选
    `memory` 变更。
2.  **旧档案先迁入，历史会话再补记。** 旧档案按 F23
    归一化写入；历史会话按当前规则重新提取，再与当前 global 对照。
3.  **复用 dream 的判定 / apply 规则，但提取提示词要单独写。** 规则（去重、冲突、不升 global、证据绑定）可以共用；提示词不行 —— dream 的输入是已有记忆（做归纳），F25 的输入是聊天原文（做抽取），两者形状不同。正常 dream 是空闲触发；补记由用户显式发起，可从会话起点扫描。
4.  **大批量补记必须先预览。** 至少显示：新增 / 更新（取代）/
    重复（NOOP）/ 拒收 数量，并允许查看明细；用户确认后才 apply。
5.  **冲突按 §3.2 处理，不生成"融合后的最终人格档案"。** 同一 `fact_key`
    的新旧值保留双时间轴；明确指令优先，旧值失效但不删除。
6.  **整次补记是一个批次，可整批撤销。** 复用 `import_batch` +
    `applied_op` / before-after
    快照；撤销前做版本校验，发生后续修改的项跳过并报告。
7.  **来源必须可追溯。** 每条候选至少记录
    `source_kind=session_backfill`、源 `session_id`、证据消息范围 /
    id；没有可定位证据的候选拒收。
8.  **增量水位必须单调推进。** 每个 `(session_id, extractor_version)`
    保存 `backfill_mark`。首次扫描 `(0, T1]`；以后只扫 `(T1, T2]`，成功
    apply 后才把水位推进到 `T2`。预览、失败、取消都**不得推进水位**。
9.  **同窗口幂等。**
    `(source_session_id, from_mark, to_mark, extractor_version)`
    建唯一约束（或等价唯一签名）；同一窗口重复执行只能复用原 run /
    返回既有结果，不能再次新增。
10. **提取器升级不自动重写历史。** `extractor_version`
    变化后，默认仍从该会话最新成功水位向前增量；若用户显式选择「按新版重新扫描历史」，创建
    `mode=reprocess` 的独立 run，从指定旧水位重扫，但 ADD / SUPERSEDE /
    NOOP 仍必须经过现有事实键和证据规则，不能因版本变化强制覆盖。
11. **不自动把所有候选升 global。** 按现有 domain→tier
    默认映射与作用域规则判断；只有满足长期价值 /
    明确跨会话语义的候选进入 global，纯会话私事保持 session。
12. **补记不等于回血。** backfill 是写入 / 归纳路径，不应伪造
    `recall_use` 或 activation 命中。
13. **预览不是锁。** 预览生成后到确认 apply 之间，目标记忆可能已被
    dream、用户编辑或另一批导入修改；apply 必须按候选记录的
    `expected_revision`
    做乐观校验。冲突项跳过并返回「需重新预览」，其余无冲突项可提交。
14. **撤销同样按 revision 校验。** 只能撤销「当前 revision 仍等于本批次
    after_revision」的项；之后被用户 / dream 修改过的项不得用旧 before
    快照覆盖，必须跳过并报告。

建议流程：

    历史 Session
      ↓ 读取增量窗口（backfill_mark..t_mark]
    extract（复用 dream 窄提示词）
      ↓
    候选记忆 + evidence
      ↓
    与当前 global / 本 session 记忆对照
      ↓
    ADD / UPDATE(SUPERSEDE) / NOOP / REJECT
      ↓
    预览
      ↓ 用户确认
    短事务 apply → import_batch

**与 F23 的边界**：

-   F23「从旧档案导入」：已经是记忆的数据，做 schema 归一、去重、迁移。
-   F25「从已有会话补记」：原始聊天还不是记忆，需要模型提取、证据绑定、冲突判定。
-   两者可以连续执行，但必须是两个独立批次，分别可撤销。
-   **copy-to（会话之间搬事件）也走同一底座**：它是 memory → memory、但跨会话，属 F23 类，不新开第三类；`import_batch.kind` 记 `session_copy`，可整批撤销。

### 3.7 批量变更底座（dream / F23 / F25 共用）

dream、旧档案导入、历史会话补记在业务触发上不同，但底层都在做同一件事：**对若干目标行提出
before → after
变更，并要求幂等、可追踪、可撤销、能处理并发冲突**。不要让三条路径各自长出一套
undo / snapshot / version 机制。

统一为两层：

-   **业务 run 表**保留各自语义：`dream_run` 负责 dream 的租约 / 水位 /
    分组进度；`import_batch` 负责 F23/F25
    的来源、预览、确认与补记水位。它们不强行合成一张表。
-   **通用变更日志 `applied_op`**承接实际写入：每个 op 记录
    `run_kind`、`run_id`、`op_idx`、`target_kind`、`target_id`、`expected_revision`、`before_json`、`after_json`、`after_revision`、`applied_at`、`undone_at`。`UNIQUE(run_kind, run_id, op_idx)`
    保证 apply 重试不重复执行。

**统一 apply 纪律**：

1.  LLM / 文件解析 / 预览都在事务外完成，只产生 plan。
2.  apply 开 `BEGIN IMMEDIATE`，逐项校验目标当前
    `revision == expected_revision`。
3.  校验通过才写目标行，并令 `revision = revision + 1`；同时写
    `applied_op`。
4.  单项 revision 冲突不允许静默覆盖。交互型 F23/F25
    返回冲突并要求重新预览；后台 dream 可跳过该项并留
    diag，下一轮重新判断。
5.  undo 反向读取 `applied_op`，仅当目标当前 revision 等于该 op 的
    `after_revision` 时恢复 `before_json`；恢复本身也产生新
    revision，不能把 revision 数字倒退。
6.  **删除 / 取代也是状态变更，不是物理删除。** 这样 before/after 和
    revision 才能统一工作；真销毁另走明确的 destructive path +
    销毁前备份。

这样 `dream_item` 可以继续保存 dream 专用的模型判定 /
分组信息，但**真正的可撤销写入凭据以 `applied_op` 为准**；避免
`dream_item` 与 `import_batch` 分别维护两套互不兼容的回放逻辑。

## 5. 界面与信息架构

### 5.1 结构原则

1.  **按用户任务切，不按实现分层切**。「会话记忆 / 全局事实」两页签是按
    `_facts.json` / `<sid>.json` 切的------判断错了（v1.4.1
    我做的）。作用域应该是**筛选器 / 徽章**。
2.  **高频在浅层**：看、加、忘、搜是高频；导入、生成档案、提炼是低频。
3.  **一个动作一个入口**：`remember 工具`
    现在同时管「自动记」和「要不要想起」，要拆开。
4.  **可见性优先**：默认让用户看见记忆在用，而不是全隐形。

### 5.2 已实现结构（1.6.14，2026-10-28 收口）

塞进一页会变成几千行，折叠区滚到底找不到（1.6.7 就踩过「点「高级」没反应」，其实是内容在最底下）。

## 6. 存储方案

### 6.1 选型

**SQLite 单库（`node:sqlite`）**，实测可用：Electron 44.7.0 / Node
24.21.0 / SQLite 3.50.4 / FTS5 可用 / 零原生编译。

-   `DatabaseSync` 同步 API，与现有「全程同步、不 await」一致
-   `journal_mode=WAL` + `foreign_keys=ON`；常规 `NORMAL`，dream
    提交与销毁 `FULL`
-   `busy_timeout` **交互路径 ≤500ms**（同步 API 会冻结事件循环，5000
    等于卡 UI 5 秒）；dream 路径更短 + 让出重试
-   **启动探针**：`PRAGMA journal_mode` 返回值不是 `wal`
    就说明盘不支持（网络盘 / OneDrive 会静默回落 `delete`）→ 提示并降级
-   备份只用同步 `VACUUM INTO`（**不能用 `backup()`**，它是
    async；目标文件必须不存在、不能开在事务里）；不能放 OneDrive /
    网络盘
-   **FTS5 只用于管理页全库搜索（F16），不进召回**（见 9.1 红线 2）

### 6.3 并发纪律

1.  一个库文件；一次业务写一个 `BEGIN IMMEDIATE` 事务
2.  **事务里绝不出现 await / LLM / 网络**
3.  回血不进大事务（幂等单行
    UPDATE：`UPDATE recall_row SET used_at = ? WHERE id = ? AND used_at IS NULL`）
4.  租约 TTL \> 单批 LLM 超时；apply 用
    `UPDATE dream_lease SET … WHERE owner = ? AND expires_at > now`
    并**校验影响行数 = 1**
5.  `backup()` 禁用，只 `VACUUM INTO`
6.  **注入路径禁止写盘**（现在每模型步 `saveStore`
    一次，`:4069`）；memory 侧按 `memSig` 指纹跳过无变化的写，trace
    侧独立单条 `INSERT`、不进 memory 事务
7.  备份节奏：**每天首写一份**（`backup/<date>/`）+
    **真销毁前一份**（`销毁前/`，保留 20 份）；`src + '.bak'`
    的「上一版」语义放弃，靠 WAL + 事务兜
8.  **所有可被 dream / 导入 / 补记 / 用户编辑触碰的主记录都带
    `revision`**；事务外生成的 plan 必须携带 `expected_revision`，apply
    时 CAS 校验，禁止 last-write-wins。
    **所有写 memory 的路径都必须带 `expected_revision`**：`/add`、`/edit`、copy-to、dream、F25 —— 漏一条 CAS 就失效。

9.  **水位与业务数据同事务提交**：F25 只有当该窗口 apply
    达到"已确认完成"的终态时才推进
    `backfill_mark`；失败、取消、仅预览不推进。

## 9. 红线与风险

### 9.1 红线

1.  **不许动检索算法**（`切词` / `稀有表` / `问句信息量` /
    `分档`），只换「候选从哪来」。现有基准 40 句真问句、精确度 43%→91%。
2.  **中文不许直接上 FTS5/BM25**（`unicode61` 把整句 CJK 当一
    token；`trigram` 只对 ≥3 字有效）。FTS5 只用于管理页全库搜索。
3.  **core 层不能复用 `stable_profile` 的鲜活度**（它返回
    `policy.unknownActivation`，用户一调旋钮 core 就掉）。
4.  **回血不许挂召回**（会自激）；**core 层必须显式禁止回血**（A 恒
    1、不建 activation 行），否则 6 条常驻事实每轮都在注入里，会自激。
5.  **稀有表 df
    的分母口径不许改**：`df.总条数 = memories.length`（合并视图）、`顶 = log((N+1)/2)`。真按
    scope 分桶算，N 和顶都变，稀有度 / C / P 全变，直接违反红线 1。
6.  **顺序稳定性**：任何会改变 `memories` 行序的改动（分页、缺省
    `ORDER BY`、去重实现、`ord` 赋值）都等价于改检索结果。
7.  **注入路径禁止写盘**：`:4069` 现在每模型步 `saveStore` 一次，S3
    要把它当成「不许保留的形态」，不是可选优化。
8.  **预算循环与常驻层允许改**：F6「core 每轮必带 +
    独立字数预算」必然要动 `:3176-3187`
    的预算循环（现在的循环会把排在后面的常驻事实按 budget
    砍掉------「每轮必带」现在并不成立）。允许改，但改完必须重跑 40
    句基准。

## 14. 待确认（剩余）

### P1 已拍板：走「adapter + 影子比对 + 分组切换」

**不采用**「换引擎不换形态」的全读全写中间态（每次仍 O(全库) 读 +

### P2 已定：`term_stat` 第一版不建（记为待办）

`term_stat` 是**词级统计缓存**（词 →
df，即这个词在多少条记忆里出现过），用来替代「每次注入都对全库切词现算稀有度」。现在
850 条量级，`稀有表`
现算只要几毫秒（`:2453-2467`），建它反而要维护增删改的一致性，而且 df
分母必须严格按合并视图算（红线 5），是个易错点。

**结论**：只建 `memory` 主表 +
查询时现算；`memory_term`（倒排）也可先不建。
